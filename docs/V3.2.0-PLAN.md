# v3.2.0 — Sistema multi-usuario con roles y permisos

**Status**: Planning
**Owner**: Rodrigo
**Target deploy**: TBD (después de aprobación de plan)

## Objetivo

Reemplazar el `ADMIN_TOKEN` único por un sistema de cuentas reales con
email + password, donde el super_admin puede invitar usuarios por email,
asignarles roles y permisos granulares por pestaña, y los invitados
crean su password vía magic link.

## Decisiones de diseño (confirmadas)

1. **Roles fijos**: `super_admin`, `admin`, `editor`
   - `super_admin`: todo, incluye gestión de usuarios y roles
   - `admin`: todas las pestañas excepto Usuarios
   - `editor`: subset de pestañas con permisos granulares (asignados por super_admin/admin)

2. **Permisos**: por pestaña con 3 niveles `read` / `write` / `delete`
   - 8 recursos: `contacts`, `stats`, `games_f2p`, `games_publishers`,
     `site_links`, `delivery`, `info_columns`, `analytics`
   - 9° recurso: `users` (solo super_admin tiene write/delete; admin tiene read si así se decide)
   - `super_admin` y `admin` tienen permisos completos por convención (no se almacena per-row)
   - `editor` lee de `user_permissions` (default: nada hasta que se le asigne)

3. **Bootstrap**: el ADMIN_TOKEN actual sigue funcionando UNTIL el primer super_admin
   set password. Primer login con ADMIN_TOKEN dispara un wizard "Setup your account"
   que pide email + nombre + password, crea el super_admin, y desactiva token-mode.

4. **Sesiones**: Cookie `monou_session` (HttpOnly, Secure, SameSite=Lax) con un
   ID firmado. Tabla `user_sessions` en DB. TTL 30 días con sliding renewal en
   cada request autenticado.

## Arquitectura

### DB schema (nuevas tablas)

```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email TEXT UNIQUE NOT NULL,
  password_hash TEXT,                    -- bcrypt; NULL hasta accept invitation
  full_name TEXT,
  role TEXT NOT NULL CHECK (role IN ('super_admin','admin','editor')),
  status TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('active','disabled','pending')),
  invited_by INT REFERENCES users(id) ON DELETE SET NULL,
  created_via TEXT,                      -- 'bootstrap','invitation'
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  last_login_at TIMESTAMPTZ
);

CREATE INDEX idx_users_email_lower ON users (LOWER(email));
CREATE INDEX idx_users_status ON users (status) WHERE status = 'active';

-- Solo aplica a role='editor'. super_admin y admin tienen todo por convención.
CREATE TABLE user_permissions (
  user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  resource TEXT NOT NULL,
  can_read BOOLEAN NOT NULL DEFAULT FALSE,
  can_write BOOLEAN NOT NULL DEFAULT FALSE,
  can_delete BOOLEAN NOT NULL DEFAULT FALSE,
  PRIMARY KEY (user_id, resource)
);

CREATE TABLE user_sessions (
  id TEXT PRIMARY KEY,                   -- 32-byte hex
  user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  expires_at TIMESTAMPTZ NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  last_seen_at TIMESTAMPTZ DEFAULT NOW(),
  ip_address TEXT,
  user_agent TEXT
);

CREATE INDEX idx_user_sessions_user ON user_sessions (user_id);
CREATE INDEX idx_user_sessions_expires ON user_sessions (expires_at);

CREATE TABLE user_invitations (
  id TEXT PRIMARY KEY,                   -- 32-byte hex
  email TEXT NOT NULL,
  role TEXT NOT NULL,
  permissions JSONB,                     -- snapshot para apply en accept
  invited_by INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  expires_at TIMESTAMPTZ NOT NULL,       -- 7 días por default
  accepted_at TIMESTAMPTZ,
  revoked_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_invitations_email_pending
  ON user_invitations (LOWER(email))
  WHERE accepted_at IS NULL AND revoked_at IS NULL;

CREATE TABLE audit_log (
  id BIGSERIAL PRIMARY KEY,
  user_id INT REFERENCES users(id) ON DELETE SET NULL,
  action TEXT NOT NULL,                  -- 'login','logout','user.create','game.update', etc.
  resource_type TEXT,
  resource_id TEXT,
  metadata JSONB,
  ip_address TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_audit_user_time ON audit_log (user_id, created_at DESC);
CREATE INDEX idx_audit_action_time ON audit_log (action, created_at DESC);
```

### Backend (server/)

**Nuevo módulo `server/auth.py`:**
- `hash_password(plain) -> str` — bcrypt con cost 12
- `verify_password(plain, hashed) -> bool`
- `create_session(user_id, ip, ua) -> session_id`
- `validate_session(session_id) -> user | None` (con sliding TTL)
- `revoke_session(session_id)`
- `get_current_user(request) -> user | None`
- Decoradores:
  - `@require_session` — debe estar logueado
  - `@require_role('super_admin' | ['super_admin','admin'])`
  - `@require_permission(resource, action)` — para `editor`
- `audit(action, **kwargs)` — log a tabla `audit_log`

**Refactor `server/app.py`:**
- Mantener `ADMIN_TOKEN` en parallel solo hasta bootstrap
- Reemplazar `verify_admin_token` por `require_session` en endpoints existentes
- Después del bootstrap: ADMIN_TOKEN se desactiva (flag en DB `system_settings`)

**Nuevos endpoints `/api/auth/`:**
- `POST /login` — email+password → cookie + user info
- `POST /logout` — invalida session
- `GET /me` — user actual + permisos (para gating frontend)
- `POST /bootstrap` — primer setup con ADMIN_TOKEN
- `POST /forgot-password` — refactor de request-token-recovery existente
- `POST /reset-password` — exchange recovery token por nueva password

**Nuevos endpoints `/api/users/`:**
- `GET /` — list (super_admin + admin)
- `POST /invite` — manda invitation email (super_admin + admin)
- `GET /:id` — detalle
- `PATCH /:id` — update role/permissions/status (super_admin)
- `DELETE /:id` — disable, no hard delete (super_admin)
- `POST /:id/resend-invitation` — re-genera token (super_admin)

**Nuevos endpoints `/api/invitations/`:**
- `GET /:id` — public, valida token, devuelve email + role
- `POST /:id/accept` — set password, crea user, auto-login

### Frontend (admin/)

**Login UI overhaul** (`admin/index.html` + `admin/app.js`):
- Pantalla actual de "Token único" → "Email + Password"
- "¿Olvidaste tu password?" → magic link recovery (refactor del existente)
- Si ADMIN_TOKEN aún válido y no hay super_admin: muestra "Setup your account" wizard

**Nueva pestaña Usuarios** (`admin/users.html` + `admin/users.js`):
- Tabla: email, nombre, rol, status, último login, invitado por
- Botón "Invitar usuario" → modal con email + nombre + role + matrix de permisos
- Click en row → edita rol/permisos (super_admin only)
- Botones Disable / Re-enable (super_admin)
- "Resend invitation" para users en status pending

**Per-tab gating**:
- Al login, frontend recibe `permissions` y oculta:
  - Tabs sin `read` → no aparecen en nav
  - Botones "Guardar" sin `write` → disabled
  - Botones "Borrar" sin `delete` → no aparecen
- super_admin/admin: ven todo

**Página pública de invitación** (`admin/invitation.html`):
- URL: `/admin/invitation/?id=xxx`
- Muestra: "X te invitó como [role]. Crea tu password."
- POST password → auto-login → redirect a admin home

### Migration / deploy strategy

1. **Schema migration**: `server/db.py::ensure_users_schema()` — corre al boot,
   idempotente, agrega tablas si no existen.

2. **ADMIN_TOKEN coexistence**: durante transición ambos paths funcionan.
   Después del bootstrap: setting `bootstrap_done=true` en `system_settings`,
   ADMIN_TOKEN-mode se desactiva.

3. **Backwards compat de endpoints**: el frontend admin existente usa
   `Authorization: Bearer <ADMIN_TOKEN>`. Se mantiene en paralelo con
   `Cookie: monou_session=xxx` durante el deploy. Luego se elimina.

4. **Deploy en single push**: backend + frontend + DB migration en un mismo
   tag v3.2.0. La DB migration corre al boot del backend.

## Seguridad

- **bcrypt cost 12** (~250ms per hash, OK para login flow)
- **Rate limiting login**: 5 intentos / 15 min / IP (ya existe el helper)
- **CSRF protection**: SameSite=Lax cookie es suficiente para POST forms;
  endpoints fetch usan custom header `X-Requested-With: monou-admin`
- **Invitations**: single-use, 7d expiry, scope email-locked
- **Sessions**: 30 días sliding TTL, revoke on password change
- **Last super_admin**: imposible de borrar/disable (DB constraint check antes)
- **Self-edit lockout**: super_admin no puede cambiar su propio role
  ni borrarse
- **Disable vs delete**: usuarios deshabilitados quedan en DB (audit trail);
  hard delete solo via SSM si fuera realmente necesario

## Decisiones confirmadas (2026-05-10)

1. **`admin` gestiona solo `editor`s**: invita/edita/disable usuarios con
   role=editor. NO toca otros admins ni super_admins. Solo super_admin
   gestiona admins.
2. **Super_admins ilimitados** con guard rail "no borrar el último".
3. **Audit log 90 días** con cleanup nocturno. Job SSM scheduled task que
   ejecuta `DELETE FROM audit_log WHERE created_at < NOW() - INTERVAL '90 days'`.
4. **Self-service signup: NO**. Solo vía invitation por super_admin/admin.
5. **2FA: NO en v3.2.0**, posible v3.2.x.
6. **Deploy incremental**: cada milestone tagged como `v3.2.0-rc1`, `rc2`, ...
   ADMIN_TOKEN sigue activo durante toda la transición hasta el final del rc4.
